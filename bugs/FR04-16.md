# FR04-16 - Web rejects a valid 11-digit 0-prefixed phone

| Field | Value |
|---|---|

## Summary

Web rejects a valid 11-digit 0-prefixed phone. This issue covers the specific condition represented by A-UI-03.

## Environment

- Baseline: `85af3ba875c88283615e22cb108f13e2fccaf0e9`.
- Selected requirement: FR04; oracle: FR-04.
- Interface: UI.
- Severity: High.
- Isolated demo source/database; no fix applied to the original SUT.

## Preconditions

Start a disposable copy of the fixed baseline. For API calls obtain a JWT through `POST /api/login`: regular user `test@eshop.com` / `Test1234!`, admin `admin@eshop.com` / `Admin123!`. These are public demo fixtures, not personal credentials. Use JSON requests and the role shown in the captured request. The server clock for API cases is fixed at `2026-10-19T08:00:00.000Z`.

Restore the target account to role=user, name=Test User, phone=0912345678 and shipping_address=1 Test Street. Keep fields other than the target condition nominal. Do not restore the fixture between the write and its readback.

## Steps to reproduce

1. Open Web `/profile` as the target regular user.
2. Enter phone `09123456789`; keep name and address nominal.
3. Click Update and record validation feedback.
4. For an accepted update, fetch the profile separately to distinguish a UI success message from persistence.

## Expected result

Update succeeds; re-login shows the exact phone.

## Actual result

The Web client rejects 09123456789 and asks for 9-10 digits, instead of accepting the required 10-11 digits starting with 0.

## Impact

A required validation, security boundary or core feature behavior is violated on the reproduced path.

The reproduced effect is limited to the observations above. Unexecuted downstream attacks, production incidents and unobserved native interactions are not claimed.

## Root cause

Profile.jsx uses /^[1-9][0-9]{8,9}$/ instead of the specified prefix/length rule.

[Affected source at the fixed baseline](https://github.com/tkob-team/eshop-sut/blob/85af3ba875c88283615e22cb108f13e2fccaf0e9/frontend-web/src/pages/Profile.jsx).

## Suggested correction

Use the shared specified validation on both client and server; keep Unicode policy explicit.
