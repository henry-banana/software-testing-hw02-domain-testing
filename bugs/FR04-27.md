# FR04-27 - SPA profile re-entry shows stale data after a successful save

| Field | Value |
|---|---|
| Finding | FR04-27 |
| Requirement | FR04 |

## Summary

SPA profile re-entry shows stale data after a successful save. This issue covers the specific condition represented by A-UI-10.

## Environment

- Baseline: `85af3ba875c88283615e22cb108f13e2fccaf0e9`.
- Selected requirement: FR04; oracle: FR-04 successful profile update and displayed persisted state.
- Interface: Browser UI via Playwright.
- Severity: Medium.
- Isolated demo source/database; no fix applied to the original SUT.

## Preconditions

Start a disposable copy of the fixed baseline. For API calls obtain a JWT through `POST /api/login`: regular user `test@eshop.com` / `Test1234!`, admin `admin@eshop.com` / `Admin123!`. These are public demo fixtures, not personal credentials. Use JSON requests and the role shown in the captured request. The server clock for API cases is fixed at `2026-10-19T08:00:00.000Z`.

Restore the target account to role=user, name=Test User, phone=0912345678 and shipping_address=1 Test Street. Keep fields other than the target condition nominal. Do not restore the fixture between the write and its readback.

Interaction fixture: phone=1912345678 is accepted by the defective Web guard although it violates SRS. This allows the save branch to be reached; SRS-valid 0-prefixed inputs are blocked by a separate validation defect.

## Steps to reproduce

1. Using the explicitly documented UI-accepted phone fixture, save a new name, confirm it via GET, navigate home with the SPA link and return to profile without reload.
2. Record the actual DOM, handler output or state transition.
3. Compare the observation and its scope with the expected criterion below.

## Expected result

After a successful profile save, returning via SPA navigation displays the persisted fields.

## Actual result

```json
{
  "at": "2026-10-20T07:43:53.025509+00:00",
  "observed": {
    "save_dialogs": [
      "Cập nhật thành công!"
    ],
    "persisted_name": "Saved Profile Canary",
    "shown_after_navigation": "Test User",
    "hard_reload_would_refetch": true,
    "phone": "1912345678"
  },
  "expected": "After a successful profile save, returning via SPA navigation displays the persisted fields.",
  "precondition": "Controlled interaction: the pre-existing phone 1912345678 is accepted by the faulty UI guard. Normal valid 0-prefixed saves are masked by the related failure; no claim that this fixture is SRS-valid."
}
```

## Impact

The server retains the successful edit, but SPA navigation shows stale account data until a fresh fetch. This can mislead the user about whether a save persisted.

## Root cause

The save handler does not update AuthContext.user; remount initializes the form from that cached object.

[Affected source at the fixed baseline](https://github.com/tkob-team/eshop-sut/blob/85af3ba875c88283615e22cb108f13e2fccaf0e9/frontend-web/src/pages/Profile.jsx).

## Suggested correction

Update or refetch shared user state after a successful save. Normal valid 0-prefixed saves are masked by the related failure; the interaction fixture is disclosed, not called SRS-valid.
